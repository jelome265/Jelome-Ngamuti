# Phase 2 — Content and Evidence

**Prerequisite:** Phase 1 layout approved.  
**Deliverable:** A verified content inventory and typed content source ready to be used in the implementation.

## 1. Objectives

1. Choose the projects that best demonstrate genuine technical work.
2. Verify every statement, status, technology, and external destination.
3. Write concise, audience-appropriate copy before placing it into components.
4. Approve which personal details and contact routes are public.

## 2. Project selection

Review candidate projects, including Sitolo, Rustacean, and Ciee’s Fashion Sense if still relevant. These are candidates, not a pre-approved final list. Inspect each source repository and current state before deciding what to feature.

Choose up to three projects based on:
- Verifiable personal contribution and evidence in source/history.
- Clear problem or intended user.
- Technical decisions that can be explained honestly.
- Enough substance to support a useful summary.
- A repository link that works and can be viewed by the intended audience.
- A clear and accurately represented current status.

Do not rank projects by novelty alone. It is acceptable to feature fewer than three.

## 3. Required content record

For each selected project, record:
- Project name and concise one-sentence purpose.
- Status: active development, completed, prototype, learning project, or archived—choose the accurate description.
- Intended user/problem.
- Personal role and scope of contribution.
- What is implemented now versus planned.
- Two or three meaningful technical decisions or design constraints.
- Evidence for claims: source files, tests, commits, deployment, screenshots, or documentation.
- Technologies actually used; do not list planned technologies as implemented.
- Repository URL and optional live demo URL, each checked.
- Optional screenshot/image, permission and license status, plus accurate alternative text.
- Any limitation that a reader should know to interpret the current state.

Where evidence is unavailable, omit the claim or clearly label it as planned or self-reported. Never manufacture impact metrics, production use, users, client results, testimonials, or completion claims.

## 4. Profile information to verify

- Public display name.
- Short positioning statement and current technical interests.
- Education/course description and current status if it is to be shown.
- Geographic label only if the owner wants it public.
- GitHub profile and selected repository destinations.
- Contact email or other intended contact channel.
- Profile image, résumé, and social links only if available, current, and approved for publication.
- Copyright/ownership and permission for any third-party imagery, logos, or quotes.

Private family circumstances, financial information, private phone numbers, passwords, and other sensitive information must not appear in public content.

## 5. Technical focus groups

Create a short list of technical areas and connect each to evidence:
- Area or technology.
- How it is used.
- Project or learning context.
- Link to a related repository or project card when appropriate.

Do not publish skill ratings, progress percentages, or “expert” labels. Prefer demonstrated work over a long unqualified keyword list.

## 6. Content module contract

Prepare typed local content modules consistent with the architecture:
- Profile: name, verified short description, optional approved contact/profile links.
- Projects: title, summary, current status, contribution, technologies, repository URL, optional demo URL, optional media/alt text.
- Technical focus: category and evidence-backed items.

Use TypeScript types to make optional destinations explicit. Avoid placeholder strings and nonfunctional links in production data. Content may be drafted in this phase; final placement in application files occurs after Phase 3.

## 7. Writing rules

- Lead with the problem, purpose, contribution, or technical decision.
- Write short paragraphs and concrete sentences.
- Separate fact from intention and aspiration.
- Prefer “building”, “prototype”, or “in development” when that is the accurate status.
- Explain technical terms when a recruiter or non-specialist may not know them.
- Never copy another developer’s biography or project descriptions.

## 8. Phase 2 acceptance criteria

- [ ] Selected projects have been reviewed against their current repositories.
- [ ] Every public claim has a source or has been removed/qualified.
- [ ] Current status, role, technologies, repository URL, and any demo URL are verified.
- [ ] Public profile, education, location, and contact details are approved by the owner.
- [ ] No placeholder projects, fake metrics, invented testimonials, or dead links remain in the content inventory.
- [ ] Draft copy fits the Phase 1 hierarchy without crowding cards or the hero.
- [ ] Final typed data fields are documented for Phase 3 implementation.
